# OpenPGP 키 서버와 keys.openpgp.org


## 1. 키 서버(key server)의 목적

**키 서버(key server)** 는 OpenPGP 환경에서
**공개키(public key, 공개키)를 배포(distribution, 배포)하고 검색(search, 검색)하기 위한 서버**이다.

키 서버의 존재 목적은 다음과 같다.

1. 공개키를 중앙에서 공유할 수 있게 한다.
2. 특정 사용자의 공개키를 쉽게 찾을 수 있게 한다.
3. 공개키의 변경 사항을 다른 사용자에게 전달한다.

중요한 점은 다음과 같다.

> 키 서버는 **공개키만을 다루며**,
> 개인키(private key)는 어떠한 경우에도 저장하거나 처리하지 않는다.


## 2. OpenPGP 키 서버의 기본 특성

### 2.1 공개키만 취급한다

키 서버에 업로드(upload)되는 정보는 다음으로 제한된다.

* primary key (주 키)
* subkey (서브키)
* UID(User ID)
* 키 역할 플래그(key usage flags)
* 만료 정보(expire date)
* 폐기 정보(revocation)

개인키는 공개키 서버의 범위에 포함되지 않는다.


### 2.2 키 서버는 “사람”이 아니라 “키”를 관리한다

키 서버는 사용자 계정(account)을 기준으로 동작하지 않는다.
대신 다음을 기준으로 키를 식별한다.

* **primary key fingerprint (주 키 지문)**

즉,

* email 주소는 식별 기준이 아니다.
* 사용자 이름은 식별 기준이 아니다.
* 오직 **키 자체**가 기준이 된다.


## 3. keys.openpgp.org의 설계 철학

**keys.openpgp.org**는 기존 OpenPGP 키 서버의 문제점을 해결하기 위해 설계되었다.

### 3.1 기존 키 서버의 문제점

전통적인 키 서버(OpenPGP HKP 서버)는 다음과 같은 문제를 가졌다.

* 허위 UID(email) 등록
* 스팸 UID 대량 삽입
* 키 정보 오염(key poisoning)
* 키 삭제가 사실상 불가능


### 3.2 keys.openpgp.org의 접근 방식

keys.openpgp.org는 다음과 같은 정책을 채택한다.

1. **email 검증(email verification)** 을 통해 UID를 제한한다.
2. **Web of Trust 서명**을 서버에서 제거한다.
3. 검증된 UID만 검색 가능하게 한다.

이로 인해 keys.openpgp.org는
“신뢰 계산”이 아니라 “키 배포”에 집중하는 서버가 되었다.


## 4. 키 서버에서의 키 업로드(upload)

### 4.1 업로드의 의미

키 서버에 공개키를 업로드한다는 것은 다음을 의미한다.

> “현재 공개키의 상태를 서버에 등록(register)하거나 갱신(update)한다”

이는 키를 생성하는 행위가 아니다.


### 4.2 업로드되는 정보의 범위

업로드 시 서버에 전달되는 정보는 다음과 같다.

* primary key와 subkey 구조
* 각 키의 역할 플래그(`[SC]`, `[S]`, `[E]`, `[A]`)
* UID 목록
* 만료 정보
* 폐기 정보

이 정보는 이후 다른 사용자가 키를 받을 때 그대로 전달된다.


## 5. 키 서버에서의 email UID 검증

### 5.1 UID와 email의 의미

공개키에는 **UID(User ID)** 가 포함되며, 일반적으로 다음 형태를 가진다.

```
이름 <email@example.com>
```

이 email 주소는 다음을 **주장(claim)** 한다.

> “이 키는 이 email 주소의 소유자이다.”

---

### 5.2 keys.openpgp.org의 email 검증

keys.openpgp.org는 이 주장을 그대로 신뢰하지 않는다.
따라서 다음 절차를 수행한다.

1. 공개키에 포함된 email 주소로 인증 메일을 전송한다.
2. 해당 메일의 링크를 클릭해야 UID가 활성화된다.

결과적으로:

* 인증된 UID → 검색 가능
* 인증되지 않은 UID → 서버에는 존재하나 검색 불가


## 6. 키의 동일성 판단 기준

키 서버에서 **같은 키인지 여부**는 다음 기준으로 판단된다.

* **primary key fingerprint**

이 기준에 따라 다음과 같이 처리된다.

* fingerprint가 같으면 → 같은 키의 업데이트(update)
* fingerprint가 다르면 → 완전히 다른 키

email 주소가 같더라도 fingerprint가 다르면 서로 다른 키이다.


## 7. 키 서버와 키 역할 플래그의 관계

키 서버는 키의 **역할(role)** 을 해석하거나 변경하지 않는다.
다만, 공개키에 포함된 **키 역할 플래그(key usage flags)** 를 그대로 저장·배포한다.

### 주요 역할 플래그

* **S (Sign, 서명)**
  서명 생성에 사용
* **C (Certify, 인증)**
  다른 키와 UID를 인증
* **E (Encrypt, 암호화)**
  데이터 암호화
* **A (Authenticate, 인증)**
  로그인 및 인증

특히,

* primary key는 보통 `[SC]` 역할을 가진다.
* subkey는 `[S]`, `[E]`, `[A]` 중 하나를 가진다.

키 서버는 이 정보를 변경하지 않으며,
클라이언트가 이를 해석하여 사용한다.


## 8. 키 서버에서의 업데이트(update)

같은 키(primary key fingerprint 동일)를 다시 업로드하면,
키 서버는 이를 **업데이트(update)** 로 처리한다.

업데이트를 통해 반영되는 정보는 다음과 같다.

* subkey 추가 또는 변경
* 만료일 변경
* 폐기 정보 추가

키 서버는 “과거 상태”로 되돌리는 기능을 제공하지 않는다.


## 9. revert(되돌리기)가 불가능한 이유

OpenPGP 키 서버는 **누적 모델(append-only model)** 을 따른다.

* 한 번 공개된 정보는 삭제되지 않는다.
* 폐기 정보(revocation)는 취소되지 않는다.
* revert(되돌리기)는 개념적으로 존재하지 않는다.

키 서버에서 가능한 조작은 다음뿐이다.

> 새로운 정보를 추가하여
> 키의 현재 상태를 변경하는 것


## 10. Revocation(폐기 선언)과 키 서버

**revocation(폐기 선언)** 은 키 서버에서 매우 중요한 정보이다.

* 폐기된 키는 서버에서 “무효”로 표시된다.
* 키는 여전히 배포되지만, 클라이언트는 사용을 거부한다.
* 이는 삭제가 아니라 **영구적인 신뢰 중단 선언**이다.


## 11. 키 서버에서의 만료(expire)

**expire date(만료일)** 는 키 서버가 그대로 배포하는 정보이다.

* 만료된 키는 서버에서 삭제되지 않는다.
* 클라이언트가 이를 해석하여 사용 여부를 결정한다.
* 만료일 변경은 업데이트를 통해 반영된다.


## 12. 키 서버 관점에서의 최종 정리

* 키 서버는 공개키만을 다룬다.
* 키 서버는 사용자 계정을 관리하지 않는다.
* 키의 정체성은 primary key fingerprint로 결정된다.
* email UID는 검색 가능 여부를 제어할 뿐이다.
* 키 역할 플래그는 서버가 해석하지 않고 그대로 배포한다.
* 같은 키 재업로드는 업데이트로 처리된다.
* revert(되돌리기)는 불가능하다.
* 폐기는 revoke(폐기 선언)로 표현된다.
* 키 서버는 신뢰를 판단하지 않고, 정보를 전달할 뿐이다.
